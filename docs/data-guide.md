# 資料維護說明

更新日期：2026-10-05。

目前第一版的資料是網站內的檔案，不需要另管理資料庫。更新檔案不會即時改變未來的公開網站；需要檢查後重新建置及發布。沒有自動更新後台。

## 新手可以怎麼提出更新

直接告訴 Codex：「請新增某景點，這是我有權使用的內容及來源」，或「請核對某張卡的官方權益與這個使用期間」。你不需要自行修改資料檔，也不要先把未授權照片下載進專案。

## 每筆資料需要有

名稱、分類、內容、資料狀態、來源、建立／修改日期、查證日期及限制。價格與位置等欄位可以分別待確認；不以範例日期冒充查證日期，不把未知改成零或「沒有」。

狀態分為：已確認、範例資料、預估資料、待確認、即時資料。第一版沒有即時資料。已確認資訊必須有可核對的來源、日期及使用範圍。

## 目前檔案與欄位

`src/data/places.json` 的每列依序是：

識別碼、名稱、類型、分類、區域、緯度、經度、停留分鐘、每人 THB 範例費用、開門小時、關門小時、偏好標籤、營業星期（可省略，範例預設每日）。

星期 0 為星期日，6 為星期六。這份簡短格式目前只適合範例。`catalog.js` 會將小時換成分鐘，補上範例來源、修改日期與「尚未查證」。**不能直接把此批資料整批改為已確認。** 未來有真實資料時，應改用逐筆具名欄位，包含官方來源及欄位確認狀態；不能讓省略欄位自動變成已確認營業。

`src/data/catalog.js` 另外保存住宿、區域、交通、銀行、信用卡、權益方案、貴賓室及推薦範本。資料識別碼不要隨意更換，已有行程會保存地點快照，避免資料更新時悄悄改寫舊行程。

排程目前使用一天一段營業區間與營業星期。特殊休業、多段／跨午夜營業尚無相應的已查證資料；納入這類真實資料之前，必須擴充欄位與排程檢查，不能直接套用目前範例時段。

## 信用卡資料必須分層

銀行 → 完整卡名與版本 → 該期間的權益方案 → 精確合作據點。

免費公告上限、個人剩餘次數、本人資格、攜伴費用、預約、會籍啟用與消費門檻要分開。Priority Pass、LoungeKey、DragonPass、銀行直接合作及航空艙等／會員權益不可互相代用。現在三種示範方案只用來測試，不是真實銀行產品。

貴賓室的「品牌」不能當成特定據點。要確認機場、國際／國內、出發／抵達、安檢前後、航廈、樓層、登機門、可達性、營業時間、停留限制與合作期間。照片、評價和條款的使用授權也要分開檢查。

## 合規更新順序

1. 確認資料與條款來源；人工閱讀也不表示可以全文複製。
2. 檢查展示、商業用途、照片、署名、保存、費用及個資限制。
3. 不明確時停止該擷取方式，先說明並找合法替代方案。
4. 在來源紀錄寫清楚核對範圍與日期，僅整理有權使用的內容。
5. 改資料，執行測試與建置，檢查搜尋、分類、詳細頁、查詢及排程。
6. 正式發布前取得所需確認。外部 API、爬蟲或需金鑰的服務另行提案，不能偷偷加入。

## 行程資料

每份行程保存版本、識別碼、名稱、曼谷時區、起迄日期、原始偏好、每日活動、地點快照、時間、個人／全團費用、備註、鎖定狀態與未安排原因。

正式行程與草稿分別保存。複製／匯入會產生新的識別碼；單日重新安排不改其他天。匯入僅接受本網站版本 1 的格式，會重新計算費用，拒絕損壞資料，不使用檔案裡的程式指令。

## 首次曼谷內容：基本來源與營運分開（已發布）

本次沒有大幅改寫既有行程結構。`open-place-facts.json` 保存 12 個 Wikidata 實體的最小欄位（英文名稱、座標、網站、機場碼及來源版本）；`first-visit.js` 保存本站原創介紹、7 個選房區域及三日動線。`catalog.js` 只對其中 10 個地點補入基本來源與座標；其餘情境維持範例。

`fact.retrievedAt` 是來源取得日期，`fact.revision` 是 Wikidata 版本，不等於營運查證。`confirmedAt` 保持 null，`hoursStatus`、`ticketStatus` 保持「待確認」，`coordinateStatus` 標示概略位置而非入口。`planningCost` 是預留估算，0 不代表免費。原本 `open`、`close`、`weekdays` 僅保留為示範排程區間，不能當成官方營業資訊；每次排程都顯示待確認提醒。

行程仍保存地點快照，包含來源與版本；新內容不會自動改寫既有已保存行程。原創三日動線提供自選午餐，沒有用虛構餐廳冒充真實推薦。更新營業時間或票價之前，仍須另外核對授權、來源及當期規則。

詳見 [本次內容與合規紀錄](first-visit-content-review.md)。

## 社群指南參考欄位（已發布）

`src/data/content-references.js` 保存 10 個地點與 4 種鐵路的指南欄位。這些欄位不合併到排程用地點：`value`、`sourceId`、`section`、`status`、`sourceUpdatedAt`、`reviewedAt`、`confirmedAt` 各自保留。`sourceUpdatedAt` 未提供時為 null，不能用閱讀日期補成更新日期；`confirmedAt` 仍為 null。沒有採用的欄位保存原因，不能改成 0 或免費。

`guideSources` 保存原文、作者歷史、版本與 CC BY-SA 4.0 授權；公開頁面及 `public/content-licenses.txt` 都提供署名。更新來源時同時更新版本、取用範圍、授權清單及查核紀錄，不能只改價格數字。

參考時段與列價不改 `open`、`close`、`weekdays`、`cost` 或使用者行程快照。只有另行完成可重用授權與當期營運核實後，才可提案將已確認欄位用於排程。新增深紅線 `cost:null` 保留未知；原有 9 種交通估算維持標示。

本批詳見 [景點與鐵路紀錄](visit-reference-review.md)。

## 餐廳指南資料（本機待發布）

`src/data/food-guides.js` 保存 6 個特定據點：`foodGuide` 含店名、店址、餐點、部分交通起點、來源章節、閱讀日期、條目日期及 CC BY-SA 4.0 署名；`confirmedAt` 保持 null。未知的餐費、座標、時段與官方網址不填猜測數字。

加入行程時 `cost:null` 表示未知；使用者自填預留額與店家售價分開。成對 null 座標可保存與匯入，地圖列出未繪入的地點。手動編輯時段界線不代表營業時間；`planningEligible:false` 保證自動排程不把不完整店家當成可到訪或免費。既有地點及已存快照不改寫。來源更新與正式發布必須同時核對授權、日期與測試，見 [本批紀錄](food-content-review.md)。
